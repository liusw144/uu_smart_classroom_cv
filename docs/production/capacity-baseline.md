# 录像批次容量规划基线

2026-11-03。用户对“每次10分钟录像、每小时一次、30分钟内完成”的示例回复“可以”。本轮先把它记录为可调整的压测假设，尚未作为正式SLA，也没有据此确定GPU型号或数量。

机器可读参数见[容量配置](../../ops/config/capacity-baseline.json)。它不包含凭据、真实素材或伪造测量。当前benchmark工具尚未读取该配置；接入完整录像批次调度与容量验收是后续工作。

| 参数 | 规划假设 |
| --- | --- |
| 学校 | 10所 |
| 摄像头来源 | 每校100个，共1000个 |
| 同批分析课堂 | 300间，每间提交一段录像 |
| 单段录像 | 10分钟 |
| 提交频率 | 每小时一批 |
| 完成窗口 | 30分钟 |
| 校内切片 | 每段最多30秒 |
| 利用率 | 按70%作为规划余量假设 |

对应每段20片、每批6000片，总录像时长50小时。假设学校均分负载，每校每批600片。片段处理速率的基本下限为6000÷1800≈3.33片/秒；按70%利用率计算，规划总处理能力约4.76片/秒、每校约0.476片/秒。这里的单位是片段，不是帧；也不代表已经测到该速度。

这只是将整个1800秒窗口都视为可用处理时间的简化推导。正式端到端验收还要明确计时起点，以及是否包含上传、校验、分段、排队、推理、编码、回传、全课汇总和AI报告。它们占用时间、CPU、磁盘、网络及显存，实际可供推理的窗口可能更短。

## 后续工程与验收

- 增加“整段录像父任务—片段清单—有限窗口提交—断点续作—全课汇总”，不把6000片一次性塞入队列，也不把片段当独立课堂统计。
- 已接入显式CPU/GPU/昇腾NPU配置，默认CPU；仍需在目标硬件确认实际算子运行位置，机器装有加速卡不会自动启用。配置入口见[推理设备配置](../guides/推理设备配置.md)。
- 固定模型、抽帧策略、分辨率及课堂人数分布，在候选硬件测量各阶段p50/p95、吞吐、显存、CPU、磁盘、排队和失败率。
- 在6000片批次、偏斜学校负载、连续多批和节点故障下验收，计入重试、保留期及存储配额影响。
- 单卡并发和多卡扩容分别测量；执行槽不能直接换算成GPU数量。模型优化之后还要复测课堂精度。

录像格式/码率、抽帧策略、存储保留天数、端到端计时边界和目标设备尚未确定。现有公开视频样例及300次HTTP入队仍只证明其各自范围，生产门禁继续保持拒绝。
