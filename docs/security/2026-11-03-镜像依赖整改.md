# 候选镜像依赖整改与剩余阻塞

本页是2026-11-03的组件扫描与整改记录，不替代已封存的源码安全扫描报告，也不把组件匹配直接判定成应用可利用漏洞。

## 已完成

Trivy 0.76.1使用本机Docker镜像和当日漏洞库完成五镜像扫描。前端初始3 Critical/65 High，先升级系统包，再由NGINX 1.28分支换至官方1.30.6 alpine-slim并复测，最新两端均0条。Java原有2 High对应系统库，升级后High/Critical为0，余1 Medium。edge由Debian slim改为独立Alpine环境，冻结依赖实际构建且原生TLS轮询通过；原45 High已去除，当前5 Medium/1 Low。

这些数量属于本次工具、漏洞库、镜像摘要和检测范围。不能由此推断前端源码、Java业务或整个产品不存在漏洞。原始及整改后JSON均保留，镜像身份由production-staging.json记录。

## 视觉镜像未放行

vision仍为Debian 13.7加发行版FFmpeg，扫描有1 Critical、212 High组件记录，High/Critical合计47个不同编号，当前报告中均无该发行版的可用FixedVersion。多个libav组件会重复匹配同一FFmpeg编号；Python语言包部分为5 Medium/1 Low。包括发行版基础工具、FFmpeg、图形/媒体传递依赖及libxml2，需要区分是否实际进入运行路径。

例如CVE-2026-6653被工具按其他来源标为Critical，而[Debian官方记录](https://security-tracker.debian.org/tracker/CVE-2026-6653)描述的是XML解析释放后使用导致拒绝服务，并将stable列为Minor/no-dsa。这个差异要求逐项校准严重性；它既不能证明本平台存在远程代码执行，也不能作为删除扫描记录的依据。

当前服务的视频解码使用OpenCV，独立FFmpeg命令用于固定rawvideo输入到H.264/MP4输出。需要进一步核对OpenCV wheel中实际打包的编解码库及版本，不能只更新系统FFmpeg就认为OpenCV解码器同步更新。进程硬限额、非root和只读容器已实测，但不是完整的代码执行沙箱，不能用这些措施直接豁免编解码风险。

## 下一步实施顺序

1. 保存实际链接库、编译选项和SBOM，按HTTP输入至OpenCV/编码子进程的真实路径逐项验证可达性。不可达判定必须有证据、负责人及复核日期，不自动批量忽略。
2. 减少视觉运行镜像中未使用的系统媒体/GUI依赖。评估从[FFmpeg官方签名源码](https://www.ffmpeg.org/download.html)构建仅包含所需rawvideo和MP4/H.264编码能力的受控发行物；同步验证OpenCV打包库与许可要求，不能随意混用Debian sid包替换稳定版ABI。
3. 对仍需处理不可信输入的原生解码器评估更强的作业隔离，避免作业进程获得服务凭据、私钥及其他学校素材；再做畸形媒体、超时/内存及崩溃恢复回归。
4. 重建镜像并重跑扫描、真实视频、资源限制和五服务TLS验收；发布使用最终digest及独立签名。上述工作尚未完成，不填入生产通过证据。
