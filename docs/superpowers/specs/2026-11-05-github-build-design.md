# GitHub 可下载构建包设计

用户选择：生成可下载的安装包。当前已有推送、PR、手动触发的完整验证，不另设跳过测试的打包入口。

采用方案：沿用 `.github/workflows/verify.yml`，在全部验证成功后构建三个独立 Python wheel，导出锁定依赖，再与当前构建的 Java JAR、两个前端静态目录组成一个 ZIP。GitHub Artifact 保存 ZIP 和外部 SHA-256；包内保存提交号、文件清单与逐文件摘要。名称使用提交号前缀，避免用 latest 混淆来源。

备选：只上传零散文件，使用时容易缺少模块和依赖说明；构建并推送 GHCR 镜像适合后续容器交付，本轮用户未选择。

约束：只从明确的构建输出和公开资料取文件；不遍历打包仓库，不包含 `.env.local`、测试私钥、模型权重、素材、虚拟环境或数据。缺少任一必要产物、遇符号链接/敏感文件、出现多个候选包时拒绝生成。CI 检查提交与工作区来源，不能将有未提交改动的本机构建冒充干净提交产物。

这是需要运行环境、数据库、Redis、模型及独立配置的服务构建包，不是 Windows EXE、离线依赖全集或生产发布。默认 CPU；GPU/昇腾驱动与硬件验收不进入普通托管 runner 的成功结论。不推送镜像、不创建 Release、不自动部署、不变更现有生产门禁。

验证：先用合成构建目录测试真实 ZIP 与摘要、缺失/多余包、敏感文件与来源校验；再实际构建三个 wheel、两个前端和隔离目录中的 Java JAR，核对 ZIP 可解压、wheel 可安装及入口可导入。校验工作流语法、根门禁，远端运行待用户提交后验收。
